## 业务并发

使用 MySQL **9.0.1** 和依赖包内 Redis **5.0.14.1**，每次新建随机名称数据库、独立 Redis 进程和随机 HTTP 端口。测试结束清理后确认没有遗留 `movie_ticket_test_*` 数据库。

| 场景 | 并发/轮数 | 验证结果 |
| --- | --- | --- |
| 同一座位抢票 | 50 请求 × 5 轮 | 每轮恰好 1 个成功；仅 1 个有效订单，库存只扣 1 |
| 25 座位同时抢购 | 50 请求 × 3 轮，每座 2 人竞争 | 每轮 25 成功、25 业务拒绝；库存为 0；每座恰好 1 单 |
| 同订单同时取消 | 20 请求 × 3 轮 | 每轮 1 成功、19 业务拒绝；库存只恢复一次，锁释放 |
| 支付与超时取消竞争 | 2 请求 × 5 轮 | 每轮仅一方成功，状态及库存一致 |
| 取票与退款竞争 | 2 请求 × 5 轮 | 每轮仅一方成功，取票标记、状态及库存一致 |

以上竞争通过业务服务入口执行，数据库、事务、SQL 更新和 Redis 为真实依赖；同座测试是并发请求，不是 50 个完整浏览器会话。预期的业务冲突不计为系统错误。

## 发现和处置

1. **积分测试预期过时，已修正并回归。** `AssistantBookingServiceTest` 仍预期 500 积分抵 5 元，但 `TicketPriceCalculator` 和支付页面都明确每单最多抵 1 元。将预期实付 65→69、83→87，积分使用量 500→100；最终 79 项快速测试无失败。
2. **首轮构建受目录权限限制。** 调整执行环境后两端完整生产构建通过，不计为产品缺陷。
3. **首轮多套程序同时启动出现内存不足。** Node、Chromium 和一次 JVM 启动报错；降低同时运行的任务数量、限制 JVM 堆后恢复。最终两端各用 2 workers 完整通过，历史会话等初轮失败未复现。
4. **Playwright 自管理服务器收尾停滞。** 初轮和单进程复测未产生完整结束统计；最终配置复用已启动的服务器，取得退出码 0 和完整 JSON 报告。未把不完整执行计为通过。
5. **本机 fetch 请求方式超时，已排除。** 原测试工具对 8080 的 13 个请求超时；使用直接 HTTP socket 与 curl 对照后服务正常。修正测试客户端后 25 项接口检查及 600 次并发请求全部通过。此项属于测试工具问题，不认定服务故障。
