一、参与者识别（Actors）

根据系统的三级权限设计（普通用户 / 影院管理员 / 超级管理员）和外部依赖识别，本系统共有 4 个参与者：

1. 普通用户 (User)

系统的 C 端用户，购票主体。

职责：浏览电影、选座购票、订单管理、退改签、咨询客服。

2. 影院管理员 (CinemaAdmin)

负责所属影院的日常运营。

职责：影厅 / 电影 / 排片 / 订单审核 / 数据查看。

3. 超级管理员 (SuperAdmin)

系统最高权限角色，泛化自影院管理员。

职责：用户管理、系统配置（含影院管理员的所有权限）。

4. 外部系统 (ExternalSystem)

非人类参与者，对接第三方服务。

职责：支付接口、AI 客服 API、电影数据 API。

用例 1：在线购票（Buy Ticket）

用例编号UC-01
参与者普通用户（User）
用例描述用户选择电影、场次、座位后下单，并完成支付获取电子票。
前置条件用户已登录；存在状态为"上映中"的电影和未来场次。
基本流程 1. 用户从首页/电影列表选择电影 → 进入详情页
2. 选择影院 + 场次 → 进入选座页
3. 系统加载座位图，并提供"智能选座推荐"（<<extend>>）
4. 用户选择 1~N 个座位 → 系统调用"锁定座位"（<<include>>，Redis 15分钟）
5. 系统调用"智能定价"（<<include>>）计算总价
6. 用户确认订单 → 进入支付页 → 模拟支付
7. 系统更新订单状态为 PAID，释放锁，标记座位为已售
8. 系统生成电子票（订单号 + 二维码）
后置条件订单状态为 PAID；座位标记为已售；用户可查看电子票。
异常流程 A1. 锁座超时：座位释放，订单状态置为 CANCELLED
A2. 支付失败：订单状态置为 CANCELLED，座位释放
A3. 座位被并发抢占：返回"座位已被占用"提示

用例 2：智能推荐（Smart Recommend）

用例编号UC-02
参与者普通用户（User）
用例描述系统根据用户画像和观影历史，混合"内容+协同+热度"算法推荐电影。
前置条件用户已登录；电影库非空。
基本流程 1. 用户进入首页 → 触发推荐请求
2. 系统检查 Redis 缓存 recommend:{userId}，命中则直接返回
3. 未命中则并行计算三种推荐：内容(40%) + 协同(30%) + 热度(30%)
4. 加权融合后过滤已观看电影，取 Top 10
5. 写入 Redis 缓存（TTL=30分钟）
6. 记录推荐日志（recommendation_log）
7. 返回推荐列表给前端
后置条件用户看到个性化推荐；缓存与日志已写入。
异常流程 A1. 新用户无画像：降级为纯热度推荐
A2. Redis 不可用：直接查询 MySQL 计算

用例 3：排片管理（Schedule Management）

用例编号UC-03
参与者影院管理员（CinemaAdmin）
用例描述管理员为某影厅、某电影创建/修改/删除场次，并设置基础票价。
前置条件管理员已登录；电影、影厅已存在。
基本流程 1. 管理员进入排片管理页 → 选择影厅
2. 点击"新增排片" → 填写电影、开始时间、基础票价
3. 系统校验时间冲突（同影厅不可重叠）
4. 系统计算结束时间 = 开始时间 + 电影时长
5. 保存排片记录到 movie_schedule 表
6. 返回成功提示，刷新列表
后置条件新场次出现在用户端可购票列表中。
异常流程 A1. 时间冲突：提示"该影厅在此时段已有排片"
A2. 已售票场次禁止删除：仅可"取消场次"并触发退款流程

七、答辩建议

  • 层次化展示：论文中先放总用例图，再分模块拆分（购票子图 / 订单子图 / 管理端子图），避免一张图过于复杂。
  • 用例描述表：每个核心用例配一份描述表（参考第四节），是答辩老师重点关注的部分。
  • 关系明确：<<include>> 用于必然发生的子流程（如下单必须锁座），<<extend>> 用于可选扩展（如智能选座是选座的可选增强）。
  • 外部系统：支付接口、AI API 作为外部参与者画出，体现系统边界，符合软件工程规范。
