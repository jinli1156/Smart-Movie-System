# 智能排片工作台与经营分析

管理端 `/smart-scheduling` 以“选择影院与日期 → 生成草案 → 时间轴微调 → 检查比较 → 确认应用”为主流程。默认排明天，支持未来 30 天；影厅按行显示，场次按实际时长定位，清场间隔以斜纹显示，黄金时段高亮，跨午夜显示“次日”。窄屏可横向滚动时间轴。

提供收益优先（75/20/5）、均衡排片（50/35/15）、丰富片单（30/25/45）三种收入/上座率/多样性权重预设；高级设置保留权重、影片上限、最低影片数、黄金场次和求解时限。可点场次换片、改时间和基础票价，也可添加、移除未锁定场次。每次微调清除旧预测，重新检查才可提交。存在未暂存修改时，切换日期、影院、刷新或离开会提供暂存后继续、放弃修改后继续和继续编辑三种选择；已暂存且没有新修改时可直接离开。暂存失败会保留当前页面和草案。

“暂存草案”将完整快照写入 MySQL 的 `scheduling_saved_draft` 表。同一账号、影院和日期保留最新一份。进入工作台、浏览器刷新或切回对应影院与日期时，会自动恢复该范围的暂存草案；也可从暂存列表手动恢复。恢复后重新检查才可应用；售票或排片快照变化时，保留暂存内容供参考并提示重新生成。读取失败会明确提示，可从列表重试。成功应用后清理当前草案对应的暂存 ID，避免再次恢复已应用的旧方案；其他标签页后来保存的新 ID 保留。

时间轴支持直接拖动未锁定场次：左右移动开场时间，跨影厅行移动更换影厅，开场时间按 5 分钟吸附，并保持原片长、票价和来源场次 ID。拖动时显示目标影厅、起止时间与清场占用，重叠、清场不足、停用影厅、过去时间或跨出目标日期会显示原因并阻止放置；允许次日散场。边缘拖动会自动横向滚动，Esc、触摸取消或拖出影厅可保留原安排。点击仍可打开编辑器；键盘聚焦场次后，左右方向键按 5 分钟调整，上下方向键切换可用影厅。触摸屏使用相同拖动交互。

将场次 A 拖到场次 B 的卡片上时，预览并交换两场的位置，不再将 B 的原占位作为重叠阻止拖动。两场保留各自影片、片长、票价和来源 ID，一次写入草案；支持跨影厅交换。同厅相邻场次按交换后的片长重新衔接，清场间隔不低于系统要求；原安排合法时保持两场合计占用的结束时间。非相邻场次或跨影厅交换使用对方的原开场位置。交换按最终两场安排检查其他占用、清场和日期约束，锁定场次不能参与交换；完成后仍需重新检查再应用。

已发布排片的首次拖动会建立草案；对照用的“原排片”和锁定场次不可拖动。有效调整会清除旧检查结果，沿用暂存、恢复、检查与确认应用流程；无效或取消的拖动保留原草案及其检查结果。前端即时冲突提示基于当前日期可见场次，相邻日期的占厅和售票变化由服务器在检查、应用时继续复查。

工作台新增三个管理员接口：

| 接口 | 用途 |
| --- | --- |
| `GET /statistics/scheduling/workspace?cinemaId=&targetDate=` | 返回整日场次、影厅、锁定原因、最小清场时间和快照版本 |
| `POST /statistics/scheduling/check` | 校验草案及相邻日期冲突，以同一预测模型计算原方案和草案指标，不写库、不逐场调用大模型 |
| `POST /statistics/scheduling/apply` | 重新校验版本与售票状态，在一个事务中应用整日变化 |

检查/应用请求包含 `cinemaId`、`targetDate`、`version`、`cleaningMinutes`、`items`。每项为 `sourceShowtimeId`（新场次省略）、`movieId`、`hallId`、`startTime`、`endTime`、`basePrice`。服务器自行判断锁定，忽略客户端预测或锁定声明；已售、待付款、已开场场次必须原样保留。新安排校验影院/影厅状态、上映日期、影片时长、票价与时间间隔。提交时锁定影院影厅和相关场次行；排片或座位台账变化返回 409，要求刷新草案。

应用保留未改动场次 ID；修改或移除的未售场次先停售并逻辑删除，新增安排使用新 ID，防止正在购买旧安排的请求误买到新安排。批量应用与手工排片共享影厅锁，任一写入失败整体回滚；重复应用旧快照会被拒绝。不会自动发布生成结果，需在工作台确认具体差异后应用。

总览、热力图、单场预测和换片模拟收进“经营分析”抽屉；推荐解释在草案下方按需展开。优化器沿用 OR-Tools，同时排除已过去的开场时间、上映日前场次及相邻日期冲突。

智能排片页的总览、单场预测、换片模拟及整日约束优化均调用 `SchedulingAiService`，复用 `DeepSeekClient`。每次请求先读取所选影院的真实场次、已支付订单、座位台账、影厅和影片，再计算统计与预测，最后将业务摘要交给大模型分析。

四个接口均返回 `aiAnalysis`，包括 `source`（`model` / `algorithm`）、`status`（`success` / `unconfigured` / `unavailable`）、模型名称、生成时间、历史样本口径、分析、优先建议和风险。模型建议仅接受本次候选证据 ID，过滤未知、重复及已售锁定候选，不改变服务器计算的数值和约束方案。模型内容按纯文本展示。

历史上座率是观测值，`estimatedRate` 是平滑需求估计；无历史样本和无时间外测试样本分别显示缺失值，不以先验或零误差冒充实测。预期上座率、收入与提升仍由可解释算法估计，MAE 不代表大模型准确率。总览平均值与预警均统计未来14天。

模型配置复用 `DEEPSEEK_API_KEY`、`AI_ASSISTANT_BASE_URL`、`AI_ASSISTANT_MODEL`。密钥放环境变量或被 Git 忽略的 `.local/assistant.properties`，例如 `DEEPSEEK_API_KEY=你的密钥`；修改后重启后端。浏览器不接收密钥。模型只接收经营统计与有限候选摘要，不接收用户账号、订单号、联系方式和取票码。

模型失败时接口保留数据库统计与算法预测，并明确显示失败状态，可在经营分析中点击“重新计算”重试。普通分析请求等待上限60秒，优化请求90秒，覆盖模型请求和求解器耗时。分析、模拟、优化与检查不写回排片；只有工作台的确认应用会修改真实排片。

验证：后端 `SchedulingAiServiceTest` 检查证据白名单、去重、锁定保护、隐私字段、模型失败和非法响应；`SchedulingIntelligenceServiceTest` 检查真实统计口径及约束求解；管理端 `e2e/scheduling-ai.spec.ts` 检查来源、空样本、降级和文本渲染。

工作台验证：`SchedulingWorkspaceTransactionTest` 在独立 H2 数据库上验证实际 MyBatis SQL、Spring 事务回滚、待付款锁定、并发售票重检、跨日冲突、旧 ID 停售与重复提交。`e2e/scheduling-workspace.spec.ts` 验证生成、比较、微调使预测失效、发布确认、冲突与过期处理、草案保留提示和桌面/窄屏布局；浏览器测试的场次与预测数据使用拦截响应，不代表真实经营效果。

时间轴交互回归同样位于 `e2e/scheduling-workspace.spec.ts`，覆盖拖动吸附、跨影厅、片长与票价保留、冲突回退、取消、锁定与停用影厅保护、边缘滚动、跨日边界、键盘调整、暂存及触摸操作。

可在管理端目录设置 `SCHEDULING_MODEL_LIVE=1` 后运行 `npx playwright test e2e/scheduling-ai-live.spec.ts`，通过真实登录、数据库和模型验证页面，并生成桌面/手机截图到 `.local/`。后端地址可用 `SCHEDULING_BACKEND_URL` 覆盖，账号可用 `SCHEDULING_ADMIN_USER` / `SCHEDULING_ADMIN_PASSWORD` 覆盖。该测试默认跳过，不自动写回排片。
