# 影票观 AI 确认下单

用户确定场次后可说“就要第二个方案，帮我下单两张”，或点击完整观影方案的“让影票观下单”。助手根据真实库存和个人优惠生成订单确认卡，显示影片、影院、日期时间、人数、座位、原价、优惠和预计实付。

用户核对后点击“确认下单并去支付”，或对当前确认卡回复“确认下单”，直接进入原有支付页，无需再经过选座页和订单确认页。用户也可以点击“自己调整座位”进入原有流程。

## 后端边界

- 新模型工具 `prepare_ticket_order` 只接受空参数，由后端注入本次观影条件；需已确定真实 `showtimeId` 和人数。编号选择继续使用 `update_watch_plan.selectOption`，不接受模型提供的用户身份或价格结果。
- 工具仅创建当前账号的订单确认卡，不创建购票订单、不锁座。确认卡在数据库中保存5分钟有效期；时间到后需重新准备。
- `POST /api/assistant/checkout/prepare` 接收 `{criteria, seats?}`，用于用户点击已有完整方案。服务端重新查询全部条件，验证人数、座位布局、占用、过道和连座，并计算真实优惠，客户端价格不能作为订单金额。
- `POST /api/assistant/checkout/{draftId}/confirm` 只接收确认卡ID，身份来自JWT。模型没有调用该接口的工具。确认时锁定对应确认记录及场次，再核验座位、场次信息、原价、券和积分报价；变化时返回409，需要重新准备并确认。
- 订单创建复用 `OrderService.createOrder`，继续使用库存条件更新及带所有者标识的Redis座位锁。确认记录与订单在同一事务提交，重复点击、并发请求、超时重试返回同一订单号；已支付或取消的同一卡片不会创建第二单。
- 外层事务若在订单插入后失败，订单及库存回滚，Redis座位锁在事务完成回调中释放。
- 下单后仅形成待支付订单，券和积分仍由已有支付接口核验并扣除。支付页带入使用券/积分的偏好，展示当前应付，用户完成支付。待支付订单延用10分钟超时取消规则。

## 界面与恢复

文字确认仅作用于当前最后一条助手消息的确认卡，其他消息继续走正常聊天。网络不确定时可重试同一确认卡，或在“我的订单”查看。切换账号或对话后，迟到响应不会自动导航到旧账号订单。

模型生成的确认卡随已有会话工具结果保存；直接点击方案生成的卡片显示在当前页面，刷新后可从“我的订单”找回已创建订单，未确认时可重新准备。历史确认卡仍需要后端重新核验，界面不据历史快照宣称已下单。
